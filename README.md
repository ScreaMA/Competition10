## 🎯 快速开始

### 项目结构

```
CoreGeek/
├── main3.py                 # 程序入口（判题系统入口文件）
├── run.sh                   # 启动脚本（判题系统调用: bash run.sh <port>）
├── pyproject.toml           # 项目配置
├── debug.log               # 完整请求响应日志（运行时生成）
├── src/agent/
│   ├── server.py           # HTTP服务器
│   ├── protocol.py         # 数据结构和协议
│   ├── grid.py            # A*路径规划
│   └── brain.py           # 决策引擎
├── tests/                  # 单元测试（pytest）
└── tools/                  # 自检与调试脚本
```

### 运行客户端

```bash
cd CoreGeek
bash run.sh 8000
```

**注意**: 判题系统使用 `bash run.sh <port>` 启动，入口为 `main3.py`；
客户端监听 `0.0.0.0:<port>`，接收判题系统的 `POST /` 请求（任意路径均可）。

## ⚙️ 核心设计

### 模块职责

| 模块 | 文件 | 职责 |
|-----|------|------|
| 入口 | `main3.py` | 解析参数,启动HTTP服务器 |
| 服务器 | `agent/server.py` | 接收POST请求,调用决策 |
| 协议 | `agent/protocol.py` | 数据结构定义,指令构建 |
| 地图 | `agent/grid.py` | A*路径规划算法 |
| 决策 | `agent/brain.py` | 白天建造,夜晚战斗策略 |

### 核心策略

**白天（70回合）** - v1.1优化后：

| 角色 | 优先级 | 行为 |
|-----|-------|------|
| 工人 | 1 | 金币≥25时建造3座武器塔（**火箭发射台、电磁狙击炮、加特林，射程优先**），**三塔分散在基地四方位（上/左/下/右）**；**塔位这一回合走不通时继续去采集/建墙，不再空手过回合**；**塔位认领只是"排队"不是"独占"——空位挑完了也跟着队友赶去的塔走，不再整队掉头去采集**；**开局两回合内塔数不低于2座**（`OPENING_MIN_TOWERS`，不看当天LLM计划） |
| 工人 | 2 | **两名工人按"矿种互补"分工**：第1名采石材（围墙材料），第2名采铁/铜换金币，不再挤在同一个矿点上 |
| 工人 | 3 | 采集石头（**批次从6降到3**），**边采边建围墙**，加快防御体系成型 |
| 工人 | 4 | 建造围墙防御圈（留右下角入口），**先封敌方来路那一侧**（`_wall_side_order`），**第5-6回合就能立起第一段** |
| 工人 | 5 | **围墙建完后，金币≥100时买升级券升级武器（level1→level2→level3）**；**武器满编满级后买围墙升级券（20金，level1→level2）**，金币不再有沉睡的出口；分工里的第2名工人从第2优先级起就负责卖矿换金币与买券，**不必等围墙圈建完** |
| 工人 | 6 | 继续采石并把多余石头（≥10）卖给小贩换金币，**形成经济循环**；没有分工矿种时退而采其他矿，背包满了先卖矿腾地方 |
| 工人 | — | **天黑前5回合停止建造与采集，回防到武器旁待命**（**火力不足2座、或围墙不足2段且手里有石材时先抢建**）；**小贩/武器商店太远、跑一趟赶不回天黑前时不出门** |
| 工人/开拓者 | 兜底 | **本回合没有任何指令时就近采矿**（石→铁→铜），保证白天不出现"整回合零动作"；任务进行中的开拓者与黄昏回防待命的角色不在此列 |
| 开拓者 | 1 | 维持进行中的任务（留在任务点旁，离开会强制结束任务） |
| 开拓者 | 2 | 提交任务答案（submitAnswer，答案取自沙盒 `executeCmd` 里执行器取到的数据；**沙盒里已解出过的同名任务命中缓存时接取后立即交卷**） |
| 开拓者 | 3 | 前往任务点领取自进化类任务（acceptTask，**每个任务80分+80金币**），**优先快过期的任务**；**任务点2占据两格，站在任意一格旁边都算到点** |
| 开拓者 | 4 | **有可接任务时全力逼近任务点（本回合走不动就原地等，不退回去跟随武器塔）**；**任务点冷却时白天守在"下一个会开放的那个"任务点旁等它开放**（不再回基地折返，天黑前按返程路费提前回防）；两个任务点都走不通时才跟随武器塔，为夜晚操控做准备 |

**夜晚（60回合）** - v1.1优化后：
1. **角色按距离就近贪心配对到武器周围1格内**（不再使用固定zip顺序）
2. 操控武器攻击射程内的机器人（跳过冷却中的武器）
3. **机器人按威胁分级（BOSS/大型 > 中型 > 小型），同级取最近**；无机器人时攻击视野内最近的敌方单位

**自进化任务** - v1.1新增完整闭环: 任务期间通过响应中的 `executeCmd` 让**执行器**在沙盒里跑一遍任务，
下一回合从请求的 `lastCmdResult` 的 `[SOLUTION]` 段里解析答案并通过 `submitAnswer` 提交（命令带任务标识，避免复用上一个任务的结果）。
**沙盒里的任务文件是"任务描述"不是答案**，执行器读任务文件与沙盒里的接口文档，
照文档给出的地址真实调用本地接口取数，取到的数据才是答案；取不到数据就什么都不打，
`_task_answer` 因此不会提交（**任务原文永远不会被当成答案交上去**，这是复盘里任务分恒为 0 的根因）。
任务描述里没写文件名时，先用 `[TASK_PROBE]` 标记的探测命令列出沙盒里的任务文件（**全盘搜索**），
下一回合从探测结果里认出文件名再按上面的流程执行取数（文件路径清单永远不会被当成答案）。
执行器一次会把沙盒里的任务文件都试着解一遍（`[SOLUTION]`/`[/SOLUTION]` 分段），
按文件名存进 `_TASK_ANSWER_CACHE`：下一个任务点领到同一个任务时直接交卷，
省掉一个来回的沙盒执行（积分随"完成回合 - 接取回合"倒扣，越早交分越高）。

**LLM 策略咨询**: 每个游戏日把额度用满，当日的前 `LLM_PROMPT_PER_DAY`（=3）个回合
各向 `prompt` 字段提交一次局面咨询（接口文档：每队每个游戏日 3 次调用额度，
当日首回合重置，自进化任务期间不计入）。可用环境变量 `LLM_PROMPT=0` 关闭。

**v1.1关键优化**（根据对战分析issue #8）:
- ✅ 围墙建造提前到第5-6回合（STONE_BATCH: 6→3）
- ✅ 任务完成闭环（submitAnswer）：每场可得160分+160金币
- ✅ 武器塔按四方位分散，避免全部挤在同侧
- ✅ 黄昏回防机制，保证首夜满火力
- ✅ 经济循环（卖石头→买升级券→升级武器）
- ✅ 攻击目标按威胁分级（BOSS优先）

**v1.2关键优化**（根据对战分析issue #10）:
- ✅ 消灭空转：工人无建造目标时按 石→铁→铜 就近采集，背包满了先卖矿换金币，不再有整回合无指令
- ✅ 入夜前火力/防线预算检查（塔<2 或 0 围墙时先抢建，再回防）
- ✅ 角色不再站到武器塔/围墙的建造点上（占住建造位会让建筑永远建不起来）
- ✅ 任务临期优先 + 冷却快结束时提前到任务点旁待命
- ✅ 沙盒输出是"文件读不到"这类错误时不提交，避免白费任务冷却

**v1.3关键优化**（根据对战分析issue #16）:
- ✅ 多名工人分头施工：塔位一经认领立即预占，工人各挑离自己最近的一座，
  不再几个人一起奔向同一座塔（复盘里"金币闲置、武器只建成1座"就是两个人挤在同一座塔上造成的）
- ✅ 建造失败换位重试：读取报文里的 `lastRoundRoleActionResults`，上一回合动作失败的单位
  改去下一个建造位，不再原地重复同一条注定失败的指令
- ✅ 任务兜底：开拓者按"临期优先、其次就近"依次尝试可接任务，最优先的任务点走不通时
  退而先去下一个，不再因为一个任务点被挡住就把两个任务点（160分+160金币）一起丢掉

**v1.4关键优化**（根据对战分析issue #15）:
- ✅ 消灭"空手过回合"：塔位这一回合走不通（无路可走/被抢占）时不再直接返回，
  而是继续往下走——有石头就建围墙，否则去采集，工人不会再围着基地来回踱步
- ✅ 矿种互补分工：两名工人里第1名采石材（围墙）、第2名采铁/铜（换金币），
  按角色ID顺序静态划定，不使用跨回合缓存；不再两名工人一起挤在同一个矿点上
- ✅ 经济不再等围墙圈：负责经济的工人从白天一开始就能卖矿换金币、用富余金币买武器升级券，
  不必等近二十段围墙全部建完（复盘里"金币连续多回合冻结"的根因）
- ✅ 经济动作不拖累夜晚火力：小贩/武器商店太远、往返一趟赶不回天黑前时不出门，
  先就近采集，避免经济工人被拖在地图另一头、夜晚武器没人操控
- ✅ 只剩一名工人（夜里阵亡后常见）时它兼顾采石与卖矿两条线，金币不会因此闲置

**v1.5关键优化**（根据对战分析issue #14）:
- ✅ **LLM建议落成指令**：prompt 里给出"本回合既定计划"（塔数/围墙配额/布防方位/任务点坐标与奖励），
  并要求回一行 `PLAN:`；`_llm_plan()` 把它解析成有界计划回灌给决策层，
  建议与指令出自同一套决策函数（复盘里反复出现的"策略与执行脱节"）
- ✅ LLM 只能拨动既有策略的旋钮（`tower` 1-3 / `wall` 0-3 / `upgrade` on|off / `defend` 四方位），
  越界值钳制、解析失败退回默认计划——LLM 不配合也不会让策略变差；
  **任务不接受关闭**（复盘指出"暂不做任务"这类建议偏保守，任务奖励是主要得分来源）
- ✅ **塔位优先罩住敌方来路**：`_calc_tower_sites()` 先按"可见的敌方基地（看不到基地时取最近的敌方单位）
  在哪个方位"排序，再按原来的"朝地图内侧空间"排序；看不到敌方单位时与原策略完全一致
- ✅ **沙盒一次取足线索**：`executeCmd` 由单条 `cat` 扩成"读任务文件 + 路径不对时按文件名
  在沙盒里再找一次 + 列出目录"，并用 `[TASK_END]` 界定答案范围、诊断信息永不当作答案提交，
  减少敌方那种"401→400"的逐次试错回合

**v1.6关键优化**（根据对战分析issue #13）:
- ✅ **空转兜底**：白天所有分支都没给角色派到活时，`_idle_gather()` 兜底派它就近采一铲矿
  （石→铁→铜），保证白天不再出现"角色整回合零指令、原地小步挪位"；
  任务进行中的开拓者与黄昏回防待命的角色除外（前者挪位会强制结束任务，后者要留在武器旁）
- ✅ **任务点按两格判定**：任务点2占据两格（任务书4.6.2），
  领取判定与"离开就结束任务"的判定都按任务点的全部格子算（`_task_distance`），
  开拓者站在另一格旁边即可 `acceptTask`，不再白绕一到两格
- ✅ **首夜防线预算**：入夜前围墙不足 2 段且手里有石材时继续铺墙
  （`MIN_WALLS_BEFORE_NIGHT`），不再立起一段围墙就把全员召回；
  没石材时仍然按原策略提前回防，不拖累夜晚火力

**v1.7关键优化**（根据对战分析issue #12）:
- ✅ **LLM 额度用满**：接口文档规定每队每个游戏日 3 次 LLM 调用额度（当日首回合重置），
  以前只在第 1 回合咨询一次，复盘里"R2、R3 请求中 prompt 为空，决策循环仅在 R1 调用了 LLM、
  指令退化为无目标移动、R3/R4 目标坐标重复"，现在当日前 3 个回合各咨询一次（`LLM_PROMPT_PER_DAY`）
- ✅ **金币闲置熔断**：金币攒到 `GOLD_FLUSH_TOWERS`（够再建两座塔）时，
  塔数配额一律提到满编（`_tower_target`），不再听凭计划把塔数压在 1~2 座后
  让金币连续多回合冻结（复盘里的"开局 75 金只花 25、余下 50 连躺三个回合"）；
  金币没到熔断线时仍然听计划的（留钱买升级券）
- ✅ **计划与执行同源**：prompt 里给出的"武器目标"座数也走 `_tower_target`，
  LLM 看到的就是执行层真正要建的座数，不会给出与指令脱节的建议

**v1.8关键优化**（根据对战分析issue #22）:
- ✅ **围墙先封敌方来路**：`_calc_wall_order()` 复用塔位那套方位判定（`_enemy_sides`），
  按"先敌方来路、其余上左下右"的方位顺序铺墙（`_wall_side_order`），
  来路先被墙压窄、再被塔罩住（复盘里"用墙把来路压缩进塔射程"）；
  看不到敌方单位时顺序与改造前完全一致
- ✅ **防守方围墙下限**：防守方每天至少保证铺好 `DEFENDER_WALL_QUOTA`（=3）段围墙
  （`_wall_target`），LLM 计划把墙压到 0 段也先留出石材施工——下限是一条连着的
  墙线（`_calc_wall_order` 按来敌方向逐格排，"单段孤立墙"机器人绕一步就进来了，
  PK592123/PK592176 里防守方全场只有 (33,12) 那一段）；进攻方不受影响，仍完全按
  计划走（地图上没有任何石材来源时下限自动失效，免得把经济线扣住、矿石卖不掉）
- ✅ **沙盒探测 SOP**：任务描述里没有文件名时（"请按沙盒里的任务说明作答"这类），
  先下发 `[TASK_PROBE]` 探测命令列出沙盒任务目录与任务文件，
  下一回合从探测结果里认出文件名再读取作答；探测输出不会被当成答案提交，
  避免开拓者卡在任务点空转整个任务周期

**v1.9关键优化**（根据对战分析issue #24）:
- ✅ **任务答案预读缓存**（`_TASK_ANSWER_CACHE`）：读任务文件时顺带把沙盒任务目录里的
  文件都读回来（`[TASK_FILE]`/`[TASK_EOF]` 分段），按文件名缓存内容；
  下一个任务点领到同一个任务时开拓者不必再等一个来回的沙盒输出，
  **接取后下一回合就能交卷**——积分 = 任务奖励 + 5 × 标准回合数 / (完成回合 - 接取回合)
  （任务书第六章），复盘的敌方就是靠 cached submit 把回合差压到 1、两次各拿 155 分，
  而我们要重读一遍沙盒、回合差至少 2；缓存是纯优化，未命中仍走原来的读取流程，
  "文件读不到"的输出不入缓存
- ✅ **建造点独占**：走去施工（目标本身是建造点）时不再整体放行建造点，
  角色不会顺路站到别的塔位/墙位上把那一格占住——复盘里"下了建造指令、
  下回合金币没扣、塔也没出现"就是这么来的；只有相邻格全是建造位、实在
  无处落脚时才退回旧行为，免得角色永远建不起来（`_valid_stand_cells`）
- ✅ **同回合建造预算**（`_gold_left`）：金币要等回合结算才扣，`turn.gold` 一直是
  回合开始时的余额，手里只够一座塔时两名工人会各下一条 build、第二条白下；
  现在按"已发出去的建造指令"把余额算出来，钱不够的工人改去采集/卖矿，
  不再发注定失败的指令
- ✅ **开拓者不退回基地**：有任务可领时不再掉到"跟随武器塔"，
  本回合走不动就原地等下一个回合——旧行为会把开拓者带回基地、下回合再往外走，
  来回打转（复盘里"开拓者整局在基地附近徘徊、从未靠近任务点"，两处任务点
  合计160分+160金币一直没人领）；有任务的开拓者也不再被"就近采集"的兜底支走

2. **自动化系统处理**:
   - 检测Issue
   - 创建分支`auto-fix/issue-123-20260912-143052`
   - 调用Claude修改代码
   - 提交并推送
   - 创建PR

3. **人工审核合并PR**

4. **合并后自动同步**: 下一轮轮询会查询这些PR的状态，一旦发现已合并，
   就把本地主干快进到远端最新，并清理已合并的本地工作分支。

### PR自动合并（免人工审批）

`auto_merge: true` 时，创建PR后会**立即尝试合并**；若GitHub尚未算完可合并性
（刚创建时常见），下一轮轮询继续重试，直到 `max_merge_attempts` 次。

| 配置项 | 默认 | 说明 |
|--------|------|------|
| `auto_merge` | `true` | 设为 `false` 即恢复“人工审核后合并”的流程 |
| `auto_merge_method` | `squash` | `squash` / `merge` / `rebase` |
| `max_merge_attempts` | `5` | 重试上限；超过后标记 `merge_failed` 并在Issue中说明，交人工处理 |

合并成功后会在Issue中回评，并紧接着把本地主干同步到最新。

> ⚠️ 这与 **设计文档 §11.7**「自动创建PR而非直接推送到main，需要人工审核后才合并」
> 的约定相反，是按使用方要求放开了人工审批环节。

### 提交隔离（避免卷进他人未提交改动）

`commit_all` **不再使用 `git add -A`**，只提交本次任务实际改动的文件；
任务开始前就已存在的未提交文件（同仓库其他人的 WIP）不会被纳入提交并会告警。
这样即使工作区里有别的开发内容，Issue 的 PR 也只会包含本次任务的改动。

### PR合并后的代码同步

每轮轮询开始时（`poll_interval`，默认60秒）执行，逻辑见
`Automation.sync_repository()` 与 `GitPusher.sync_main()`：

| PR状态 | 动作 |
|--------|------|
| 已合并 (`merged=true`) | `fetch` → 切到主干 → 同步到 `origin/主干` → 清理已合并的本地分支 |
| 已关闭未合并 | 标记完成，不再跟踪，不同步代码 |
| 仍开放 | 什么都不做，下轮再看 |

**同步策略**（`sync_strategy`，本地与远端分叉时生效）：

| 取值 | 行为 |
|------|------|
| `rebase`（默认） | 把本地提交重放到远端之上，保持线性历史 |
| `merge` | 生成一个合并提交 |
| `ff-only` | 只允许快进，分叉时保持现状（最保守） |

> 实际使用中本地几乎总是「又领先又落后」（本地有自己的提交 + 远端有你刚合并的 PR），
> 所以只做快进等于永远不同步，默认才用 `rebase`——等价于 `git pull --rebase`。

**安全约束**：

- 优先快进（`--ff-only`）；需要 rebase/merge 时一旦冲突立即 `--abort` 回滚，
  保证不留下半成品，也绝不用远端覆盖本地提交
- 工作区有未提交改动时直接跳过（同步失败不标记完成，下轮自动重试）
- 清理本地分支用 `git branch -d`（未合并的分支会拒绝删除）
- 远端分支默认保留，需要删除时把 `delete_remote_branch_after_merge` 设为 `true`
- 不想要这个行为就把 `auto_sync` 设为 `false`

## ⚠️ 注意事项

1. **稳定性优先**: 异常处理必须完善，程序不能崩溃
2. **性能要求**: 每回合决策时间<1秒（实测平均约1.5ms）

7. **启动方式**: 判题系统使用 `bash run.sh <port>`，入口为 `main3.py`
8. **提交前自检**: `python -m pytest tests/ -q` 与 `python tools/local_check.py` 均需通过

## ❓ 常见问题

### 本地 push 弹出 GitHub 账号选择框

**原因**: Git for Windows 在系统级 gitconfig 里配了 `credential.helper=manager`（GCM），
它排在 `store` 之前；git 会按「系统 → 全局 → 本地」顺序把 helper 追加成链，
GitHub 无可用凭据时 GCM 就弹账号选择框。URL 级配置只是追加、不会替换，所以必须在
本地作用域用**空值清空整条链**再指定 `store`：

```bash
cd <仓库根目录>            # 即 Competition10/
git config --local credential.helper ""
git config --local --add credential.helper store
```

凭据本身取自 `~/.git-credentials`（内容形如
`https://x-access-token:<PAT>@github.com`）。验证方式（应只看到 `credential-store`）：

```bash
GIT_TRACE=1 git push --dry-run origin main 2>&1 | grep credential
```

> 自动化系统自身的推送不受影响：它在推送 URL 里直接携带 token，不经过 helper。

### 自动化处理Issue后“没改代码”

**排查顺序**:

1. 看 `automation/automation.log` 里 `executing claude for issue #N` 那行的
   `prompt=X chars/Y lines`。如果 X 很小、Y=1，说明提示词在传给 Claude 前就被截断了。
2. 看紧随其后的 `claude summary:`：这条会把 Claude 的原话记下来，能直接看出它是
   “没看到需求”还是“看过代码后判断无需修改”。

提示词是**多行文本**（标题、正文、要求各占一行），早期实现把它作为命令行参数传给
`claude`，在 Windows 上会被截断在第一行：`shutil.which("claude")` 解析到的是 npm 生成的
`claude.cmd` 垫片，参数经 `cmd.exe` 解析时换行等同于命令结束，Issue 的标题与正文整段丢失。
现在改为在 `-p` 模式下把提示词从 **stdin** 送入（`automation/executor.py` 的
`_build_invocation`），既不受换行影响，也绕开了 Windows 约 32K 的命令行长度上限。

验证方式（改动提示词传递后）：

```bash
cd <仓库根目录>
python automation/automation_main.py --once   # 处理完一轮即退出
```

日志中若出现 `prompt=... chars/<N> lines`（N>1）且 `claude summary:` 里引用了 Issue 正文，
即说明提示词已完整送达。
