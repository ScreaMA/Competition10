## 三、改动清单

### T1 塔型顺序（已完成，仅存档）

`brain.py:87` 已是 `(ROCKET, RAILGUN, GATLING)`，注释里也写明了射程理由。
聊天记录建议的「2 导弹 1 电磁」需要同型号建两座，当前 `TOWER_LOADOUT`
是三种各一座。**是否改成 `(ROCKET, ROCKET, RAILGUN)` 需要先确认判题系统
是否允许同型号多建**（任务书未明确禁止，但也没有例子）。

- 风险：低（改一个常量）
- 前置：确认同型号可重复建造
- 建议：先在 `local_check.py` 里用真实报文验证 build 指令返回成功

### T2 塔位可达性校验（P0，聊天记录的核心结论）

**问题**：`_calc_tower_sites`（`brain.py:1590` 附近）按上/左/下/右四方位
各取一个代表点，只校验 `turn.land(neighbor)`（该格可通行），**没有校验
「塔建成后，操控者还能不能走到塔旁边」**。三座塔一旦把 6×6 区域的通道
切断，就会出现聊天记录里说的「有一个炮塔碰不到」——塔在，但没人能操控，
等于白扔 25 金。

**修法**：候选塔位组合选定后，做一次连通性预演：

```python
def _tower_sites_reachable(turn, sites) -> bool:
    """假设 sites 全部建成后，每座塔旁是否仍至少有一个可达落脚点"""
    blocked = set(sites)  # 塔占格视为不可通行
    for site in sites:
        neighbors = [n for n in get_neighbors(site)
                     if n not in blocked and turn.land(n)]
        if not neighbors:
            return False   # 这座塔被自己的邻居堵死
        # 从基地出发能否走到 neighbors 中任一格（BFS，把 blocked 当墙）
        if not _bfs_any(turn, turn.station().pos, neighbors, blocked):
            return False
    return True
```

选位时按「朝向地图内侧」排序取前三，若 `_tower_sites_reachable` 为假，
换下一个组合（四方位取三，共 4 种组合，穷举成本可忽略）。

- 影响：避免整局白扔一座塔 + 一个角色夜晚空转
- 风险：中（新增 BFS，需覆盖「基地被围墙包住」的边界）
- 测试：造一个「三塔堵死唯一通道」的地图，断言换位后可达

### T3 基地升级券（P1）

**问题**：全库无 `StationUpgrade` 相关实现。基地残血时没有任何自救手段，
而聊天记录明确说升级券能「回满血还顺便升级」。

**阻塞项**：`protocol.py:104` 的 `Unit` **只有 `health`，没有 `max_health`**
（已核实字段列表：`unit_id/pos/kind/health/level/cooldown/attack_range/
attack_power/capacity/backpack`）。判断「残血」需要满血基准。

两条可选路径：

1. 用任务书 4.5.1 的血量表按 `level` 反查满血值，硬编码成常量表
2. 记录开局第一回合的 `health` 作为满血基准（但本模块是无状态设计，
   与 `brain.py` 顶部注释的「不依赖任何跨回合的战场状态」冲突）

**推荐路径 1**，与现有 `WEAPON_UPGRADE_VOUCHERS` 表同构：

```python
STATION_MAX_HEALTH = {1: ..., 2: ..., 3: ...}  # 取自任务书4.5.1
STATION_HEAL_RATIO = 0.5  # 血量低于一半才用券

def _emergency_station_upgrade(turn, worker, commands) -> bool:
    station = turn.station()
    full = STATION_MAX_HEALTH.get(station.level)
    if full is None or station.health > full * STATION_HEAL_RATIO:
        return False
    ...  # 买券 → 走到基地旁 → use_command(券名, station.pos)
```

- 前置：**从任务书 4.5.1 抄出基地血量表和券名**（券名当前未知，
  武器券叫 `WeaponUpgradeVoucher1`，基地券命名待查）
- 风险：中（券名猜错会导致 buy/use 全部失败，需先用报文验证）

### T4 围墙修复包 WallFixer（P2）

**问题**：全库无 `WallFixer` 字样。围墙掉血后只能拆了重建（费石材），
聊天记录说这个道具 10 金、3×3 范围回满，**配合角落站位一次奶 5 段墙**
（见 `新版站位-角落WallFixer.png`）。

**修法**：在 `_upgrade_weapon_with_gold` 同级加一条金币用途，优先级排在
武器升级券之后、围墙升级券之前（10 金比 20 金的围墙券便宜，且救急）：

```python
WALL_FIXER = "WallFixer"      # 券名待从任务书/报文确认
WALL_FIXER_GOLD = 10
WALL_FIXER_RADIUS = 1         # 3x3 即半径1

# 触发条件：视野内有掉血围墙 ≥3 段，且存在一格能同时覆盖它们
```

同样卡在满血基准上（围墙 `Unit` 也只有 `health`），依赖 T3 的血量表。

- 风险：中（依赖 T3，且需要「找最优覆盖格」的小型搜索）

### T5 极限经济（P2）

**现状**：`GOLD_FLUSH_TOWERS`（`brain.py:137`）保证金币不闲置，
`OPENING_MIN_TOWERS = 2`（`brain.py:99`）保证开局两回合内两座塔。
但**没有「首日攒到 200 金」这个目标**，金币一到 100 就买武器券花掉了。

聊天记录说的路线是：首日 3 塔 + 攒 200 金 → 次日升 2 座塔。
这与当前「见 100 就升级」的贪心策略冲突，改动会牵动 `_llm_plan` 的配额
逻辑，**收益不确定**（升 2 座 level2 vs 早升 1 座），建议放在 T2/T3 之后。

- 风险：高（动经济主干，容易把已经跑通的节奏改坏）
- 建议：先不动，等 T2/T3 上线后用对战数据对比再定

### T6 人肉城墙（P3）

石材不够时，让角色站在围墙缺口上当肉盾（见 `人肉城墙堵缺口.png`）。
当前 `_fall_back_to_weapons` 只把角色收回武器旁，不考虑堵口。

风险最高的一项：角色站缺口会挨打，且占位可能挡住自己人的路径（与 T2
同一类问题）。**建议 T2 的可达性校验先落地，再考虑这个。**

## 五、待确认清单

动手前需要从任务书 / 真实报文里确认：

1. **同型号武器能否重复建造**（决定 T1 是否改成 2 导弹）
2. **基地升级券的道具名**（`use_command` 的 `name` 参数，武器券是
   `WeaponUpgradeVoucher1`，基地券命名规则未知）
3. **围墙修复包的道具名**（聊天记录只给了中文名和 10 金的价格）
4. **各等级建筑的满血值**（任务书 4.5.1，T3/T4 都要用）
5. **`weaponShopList` 报文里是否真的有这两种道具**（不在售就不用做）

前 4 项没确认之前，T3/T4 只能写框架不能上线——券名错了会导致 buy/use
静默失败，比不做更糟（金币白花，且 `fail=[]` 日志里看不出原因）。
