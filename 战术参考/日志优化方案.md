# 日志优化方案

> 目标：让 `debug.log` 单文件就能填满[对战分析模板.md](./对战分析模板.md)的每一格，
> 不需要人工翻全量报文、不需要跨回合心算差值。

## 一、当前日志实况

代码位置 `CoreGeek/src/agent/server.py`（227 行，最近一次改动见 commit `ecc4aca` #32）。
每回合固定打 2~3 行 INFO，全量 JSON 只进 DEBUG（`debug.log`）。

### 1.1 现有三条 INFO

| 日志行 | 字段 | 来源 |
|-------|------|------|
| `request_decoded` | `id round team team_type roles gold score base towers walls robots mines tasks phase fail` | `server.py:147` |
| `sandbox_result` | `id round text`（300 字预览） | `server.py:164`，仅任务期 |
| `strategy_done` | `id round commands elapsed sandbox actions` | `server.py:186` |

外加两条非常规行：`decision slow`（>800ms 告警，`server.py:191`）、
`decision failed`（异常堆栈，`server.py:204`）。

### 1.2 现有字段的粒度

已经做得不错的：

- `robots=12(s8 m3 l1 b0)` —— 按种类拆开了，波次构成能看（`_robot_brief`）
- `tasks=[自进化类1@(30,12)可接/50回合] phase="..."` —— 任务点状态 + 当前任务描述（`_task_brief`）
- `fail=[3 7]` —— 上回合执行失败的角色 ID（`_failed_brief`），这是排"指令下了但没生效"的唯一线索
- `actions=3:build→(11,22) railgun 7:collect→(25,3)` —— 每个角色干了什么（`_actions_brief`）

## 三、改造方案

原则：**INFO 行保持单行、机器可解析**（`analyze_log.py` 按行正则提取），
新字段一律追加在行尾，不破坏现有正则。

### 3.1 `request_decoded` 扩字段

现有（`server.py:147`）：

```
request_decoded id=1 round=1 team=4321 team_type=challenger roles=9
gold=75 score=0 base=(30,10) towers=3 walls=5 robots=12(s8 m3 l1 b0)
mines=12 tasks=[...] phase=- fail=[]
```

改为：

```
request_decoded id=1 round=1 team=4321 team_type=challenger roles=9
gold=75 score=0 base=(30,10) hp=1500/1500 towers=3[rocket2 railgun1 gatling1]
walls=5[l1:3 l2:2] robots=12(s8 m3 l1 b0) kills=7
enemy_gold=- enemy_score=8 enemy_towers=3 enemy_walls=4
mines=12 bag=stone:6,iron:2 tasks=[...] phase=- fail=[]
```

新增字段说明：

| 字段 | 来源 | 填的缺口 |
|-----|------|---------|
| `hp=1500/1500` | `turn.station().health` / 任务书血量表 | G2 |
| `towers=3[rocket2 railgun1 gatling1]` | `_tower_brief()`（新增） | G3 |
| `walls=5[l1:3 l2:2]` | `_wall_brief()`（新增） | G4 |
| `kills=7` | 见 3.3 的 `_kill_counter` | G6 |
| `enemy_score=8` | `payload["teamEnemy"]` 里的积分 | G1 |
| `enemy_towers/walls` | `turn.enemies` 按 kind 统计 | G1 |
| `bag=stone:6,iron:2` | `worker.backpack` 合并计数 | G11 |

**注意**：`enemy_gold` 报文里**没有**（`teamEnemy` 只给 `roles`），
接口文档确认过。敌方经济只能通过「敌方塔/墙数量变化」间接推断，
日志里打 `-` 即可。

### 3.2 `strategy_done` 扩字段

现有（`server.py:186`）：

```
strategy_done id=1 round=1 commands=3 elapsed=2.22ms sandbox=空闲
actions=3:build→(11,22) railgun 7:collect→(25,3)
```

改为：

```
strategy_done id=1 round=1 commands=3 elapsed=2.22ms sandbox=空闲 gold_spent=25
actions=3:build→(11,22) railgun 7:collect→(25,3) 9:attack→(28,11) smallRobot
```

| 字段 | 来源 | 填的缺口 |
|-----|------|---------|
| `gold_spent=25` | 本回合 build/buy 动作的理论花费 | G9 |
| attack 目标型号 | `_find_attack_target` 返回时带上 `robot.kind` | G13 |

`gold_spent` 只是**理论值**（按任务书价格表算），实际扣款以
下一回合 `gold=` 差值为准——两者不一致就说明有指令被拒。

### 3.3 新增 `round_end` 汇总行

在响应发送后追加一行，专供对战分析：

```
round_end id=1 round=1 gold=50 hp=1500/1500 towers=3[rocket2 railgun1 gatling1]
walls=5[l1:3 l2:2] kills=2/3 idle_weapons=1 loses=0
```

| 字段 | 含义 | 填的缺口 |
|-----|------|---------|
| `kills=2/3` | 本回合击杀 2 台 / 场上共 3 台 | G6 |
| `idle_weapons=1` | 射程内无目标 **且** 无人操控的塔数 | G12 |
| `loses=0` | 本回合损失的单位数 | — |

`idle_weapons` 的定义要明确：**无人操控**（角色不在塔旁）才算空转；
有人操控但没目标（射程内无机器人）不算——两者的问题性质不同，
前者是回防失败，后者是射程覆盖不足。建议拆成两个字段：

```
idle_man=1     # 无人操控的塔
idle_target=0  # 有人操控但射程内无目标
```

### 3.4 每日汇总 `day_summary`

每 130 回合（`ROUNDS_PER_DAY`）打一行总账，省掉人工跨回合累加：

```
day_summary day=1 gold_peak=120 gold_final=95 build=8 upgrade=2 sell=14
task_accept=2 task_done=1 score_gain=80 hp_lost=210 kills=23
```

这一行能直接填满模板 §1.2 时间线和 §6 失分点两节。

### 3.5 动作失败原因 `fail_reason`（G8）

当前 `fail=[3 7]` 只给角色 ID，不说为什么。判题系统不回原因，
但可以**自查**——失败指令和上一回合的 `actions=` 对照：

```
fail_reason 3=move目标被占用 7=collect距离不足
```

实现方式：在 `decide()` 里记录每个角色「为什么选了这个动作」，
失败时把原因串起来。这需要 `brain.py` 配合，改动比前面几项大。

**降级方案**（成本低）：只标出失败动作的类型，不猜原因：

```
fail=[3:move 7:collect]
```

一半的信息量，但不用动 `brain.py`。

## 四、实施顺序

按「填模板价值 ÷ 实现成本」排，前三项能覆盖 80% 的分析需求：

| 顺序 | 改动 | 位置 | 成本 | 填的缺口 |
|-----|------|------|------|---------|
| 1 | `hp=` 基地血量 | `server.py:_base_brief` 扩写 | 极低（改一个函数） | G2 |
| 2 | `towers=[类型:等级]`、`walls=[等级分布]` | 新增 `_tower_brief` / `_wall_brief` | 低 | G3 G4 |
| 3 | `enemy_score/towers/walls` | `request_decoded` 追加 | 低 | G1 |
| 4 | `round_end` 汇总行 | `server.py` 响应后 | 低 | G6 G12 |
| 5 | `day_summary` 每日总账 | `server.py` 判断 `round % 130 == 0` | 低 | 模板 §1.2 §6 |
| 6 | `fail=[3:move]` 带动作类型 | `_failed_brief` 关联 `actions` | 中 | G8 |
| 7 | `gold_spent=` | `strategy_done` 追加 | 中 | G9 |
| 8 | `bag=` 背包占用 | `request_decoded` 追加 | 低 | G11 |
| 9 | `idle_man/idle_target` | `brain.py` 回报 | 中 | G12 |
| 10 | `fail_reason` 具体原因 | `brain.py` 决策理由回传 | 高 | G8 |

### 4.1 前三项的最小改动量

1~3 项全部在 `server.py` 的 brief 函数里，不碰决策逻辑：

```python
def _hp_brief(turn: Turn) -> str:
    """基地血量（我方）——胜负的第一判据"""
    station = turn.station()
    if station is None:
        return "hp=-"
    return f"hp={station.health}/{_station_full_health(station.level)}"

def _tower_brief(turn: Turn) -> str:
    """武器明细：类型+等级，如 3[rocket2 railgun1 gatling1]"""
    weapons = turn.weapons()
    detail = " ".join(f"{w.kind}{w.level}" for w in weapons)
    return f"{len(weapons)}[{detail}]" if detail else "0[]"

def _wall_brief(turn: Turn) -> str:
    """围墙等级分布，如 5[l1:3 l2:2]"""
    walls = turn.walls()
    if not walls:
        return "0[]"
    counts: dict[int, int] = {}
    for wall in walls:
        counts[wall.level] = counts.get(wall.level, 0) + 1
    detail = " ".join(f"l{lvl}:{n}" for lvl, n in sorted(counts.items()))
    return f"{len(walls)}[{detail}]"
```

`_station_full_health(level)` 查任务书 4.5.1 的血量表——**与 T3 共用同一张表**，
这正是「日志优化」和「战术参考修改建议」的交汇点：日志先把血量打出来，
对战分析才能判断「基地残血时有没有用券」，T3 的触发条件才可验证。

### 4.2 敌方信息的边界

`enemy_score` 来自 `payload["teamEnemy"]`，但接口文档说明敌方只有
「基地和围墙全图可见，其他单位需进入视野」。所以：

- `enemy_towers` 在视野外会是 0——**这是正常的，不是日志 bug**
- 分析时要把「敌方塔数为 0」区分成「真的没有」和「没看见」，
  建议日志里再带一个视野计数：`enemy_visible=2`（我方视野内单位数）

### 4.3 不要做的事

- **不要把射程覆盖判定塞进日志**（G7）——那需要知道机器人路径，
  是分析侧该算的，日志只负责给原始坐标
- **不要打全量 JSON 到 INFO**——已有 DEBUG 兜底，
  `analyze_log.py` 按行解析，多行会拆散记录
- **不要在 INFO 里打机器人逐个坐标**——41×32 地图上几十台机器人，
  一行几千字符，频率又高，`debug.log` 会爆

## 五、验收方式

改完后，用真实对战日志跑一遍：

```bash
cd CoreGeek
python tools/analyze_log.py            # 现有统计
python tools/analyze_log.py --template # 按分析模板生成骨架（建议新增）
```

新增 `--template` 选项后，脚本直接把 `debug.log` 渲染成
[对战分析模板.md](./对战分析模板.md) 的填空版——能自动填的填上，
填不了的留 `{待人工}`。这样每场对战的分析成本从「翻几千行日志」
降到「核对几个空格」。

**验收标准**：模板 §1.1 的 8 行关键数据，`--template` 能自动填出 6 行以上
（其余 2 行是敌方经济，报文里没有，属正常缺失）。
