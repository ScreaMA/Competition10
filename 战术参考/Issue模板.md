# Issue 提交模板（对战分析 → 自动修复）

> ⚠️ **历史存档（V1）。** 客户端已整体重写，文件路径与约束都变了。
> **新 Issue 请用 [Issue总结模板V2.md](./Issue总结模板V2.md)**（配套
> [日志分析模板V2.md](./日志分析模板V2.md)）。

> 这份模板是和[对战分析模板.md](./对战分析模板.md)**成对**的：
> 分析模板负责「往下读」（从日志里挖问题），
> 本模板负责「往上写」（把问题写成自动化系统能吃的 Issue）。
>
> 两边的字段一一对应，见文末对照表。

## 一、自动化系统怎么读 Issue

`automation/issue_monitor.py` 按标签筛选，`dispatcher.py` 提取提示词。
对战分析类 Issue 必须同时带这两个标签：

```
Labels: auto-fix, battle-analysis
```

提取规则（`dispatcher.extract_claude_prompt`）：

- Issue 正文里有 ` ```claude-prompt ` 围栏时，**只取围栏内的内容**作为提示词
- 没有围栏时，整个正文当提示词（但会自动加上「请分析需求」的引导语）
- 提示词里**必须包含文件路径**，否则 Claude 不知道改哪

## 三、写 Issue 的注意事项

### 3.1 必须带的字段

| 字段 | 为什么必须 |
|-----|-----------|
| `Labels: auto-fix, battle-analysis` | 少了标签系统不会处理 |
| `claude-prompt` 围栏 | 没有围栏时提示词会掺进整篇报告，Claude 容易跑偏 |
| §4 里的**文件路径** | 没路径 Claude 要全库找，容易改错文件 |
| §3 里的**回合号** | 让 Claude 能回原始日志核对，而不是凭空改 |
| §4 里的**预期效果** | 自动化系统跑完测试后靠这个判断改对了没 |

### 3.2 建议这么写

- **一条建议一个文件**：S1 改 `brain.py`、S2 改 `server.py` 时分开写，
  混在一起 Claude 容易只改一半
- **常量名写全**：写 `STONE_BATCH = 6 改成 3` 而不是「把采集批量改小」——
  后者 Claude 要猜是哪个常量
- **带上「别改什么」**：明显的边界（如「不要动 protocol.py 字段名」）
  能避免 Claude 顺手重构

### 3.3 不要这么写

- **不要写「优化策略」**这种没有落地点的建议——Claude 只能瞎改
- **不要一次提超过 3 条建议**——`automation_config.yaml` 里
  有单次处理上限，超出的会被截断
- **不要建议改 `main3.py` 或 `run.sh`**——这两个是判题系统入口，
  动了可能整个跑不起来

## 四、两个模板的字段对照

| 对战分析模板（读） | Issue 模板（写） | 日志字段来源 |
|------------------|----------------|-------------|
| §1.1 关键数据对比 | §1 战况概览 | `request_decoded` 的 `hp=` `score=` `towers=` |
| §1.2 时间线 | §2 关键时间线 | `day_summary` |
| §5.1 夜间防守表 | §1 击杀行 | `round_end` 的 `kills=` |
| §6.1 直接失分项 | §3 发现的问题（P1/P2） | `fail=` + `sandbox_result` |
| §8.2 决策逻辑问题 | §4 建议（带代码位置） | `actions=` 反推 |
| §9 优化建议（P0~P3） | §4 建议（S1/S2/S3） | — |
| §10 行动计划 | `claude-prompt` 围栏 | — |

**关键**：分析模板 §9 的优先级（P0/P1/P2/P3）直接决定 Issue 里建议的**条数和顺序**——
P0 必须写进 `claude-prompt`，P3 可以只留在报告里不进围栏。
